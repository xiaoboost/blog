# 名词解释

*插件 (Component)* 对应论文中的 Component，描述插件的依赖、供给和加载过程。
*插件实例 (Fiber)* 指插件进入运行时后产生的具体实例。
*副作用 (effect)* 指对共享环境的修改，本文沿用前端的译法，不译作“效应”。
*撤销函数 (inverse)* 比通常的 cleanup / disposer 多一层约定，不仅负责清理，还必须真正撤销对应操作。
*上下文需求 (coeffect)* 描述插件要求环境提供什么，例如文件系统或日志服务。

# 它到底讲了什么

## 我是不是看错论文了

前些日子 DeepSeek 发布了自己的 [Agent Harness](https://github.com/deepseek-ai/deepseek-harness)，社区里出现了很多介绍。我也陆续看了一些介绍，但这些内容大多集中在它的核心理念：*Everything is a Plugin*，万物皆插件。模型、工具、记忆和会话都可以是插件，甚至 Agent Loop 本身也可以被替换。还有不少文章会继续深入源码，解释 DSH 如何执行任务、调度工具，以及 Agent Loop 如何推动整个过程。我最近也在学习 Agent Harness，很自然地想看看它的设计，以及它与 Claude Code、Pi 有什么不同。带着这个期待读完官方提供的[论文](https://arxiv.org/abs/2608.25512)，我的第一反应却是：我是不是看错论文了？

这篇论文几乎没有讨论 Agent 本身的运行机制，也没有解释 DSH 的 Agent Loop 究竟如何运行。至于模型怎么规划任务、调用工具、组织上下文，以及网上诸多源码解读里谈到的 Agent 架构和调度机制，那就更没有了。我把社区对 DSH 整体架构的讨论，当成了论文要解释的内容。
实际上，DSH 是一个 Agent Harness，Cordis 是它底层的插件运行时，论文研究的是后者背后的问题。一个允许插件动态安装、卸载和替换的系统，怎样才能在变化中保持正确？

我又产生了新的疑问，为什么一个 Agent Harness，需要一篇讨论插件运行时的论文？

## 自演化的 Harness 意味什么

要回答这个问题，首先要理解论文所说的“自演化 Harness”究竟在演化什么。模型之外的工具、记忆、存储和调度，共同组成了 Agent 赖以工作的 Harness。模型可以在其中选择工具、读写记忆，但使用这些能力，与修改承载它们的系统，是两件事。

论文设想的自演化关心后者。如果未来的 Agent 能够修改自己的 Harness，工具、模型服务乃至核心循环，就需要成为它可以识别和操作的对象。这里首先需要的不是更灵活的调用方式，而是让 Harness 把自身结构表达出来。
把这些组成部分纳入统一的插件模型，就为描述和修改系统提供了共同语言。这是理解 DSH“万物皆插件”的一个入口。插件化并不是自演化的充分条件，却让自演化有了可操作的对象。

## 所谓“万物皆插件”

这个理念在工程领域并不陌生。Webpack 的[官方文档](https://webpack.js.org/concepts/plugins/)就说明，它自身也建立在用户使用的那套插件系统之上。不过，高度插件化，与运行中安全地改变插件组合，还不是同一件事。

Webpack 的插件会把回调注册到 Hook 上，再在相应的编译阶段执行。常规配置下，参与工作的插件集合相对稳定，动态的是这次执行哪些回调。类似地，模型从已经注册的工具中选择一个，也不意味着 Harness 的结构发生了变化。
Cordis 关心的则是另一种动态。插件可以在进程运行期间进入、退出和被替换，变化的是系统里有哪些插件，以及它们之间怎样绑定依赖。这一区别可以理解为“动态调用”与“动态组合”，而不只是代码有没有提前加载进内存。

## “万物皆插件”之后

把能力变成插件，只解决了如何组织和接入它们，没有自动解决替换时的状态清理与依赖协调。重启可以回收许多进程内资源，再按配置重新组装系统；但如果希望保留长期会话和仍在进行的工作，就需要更细的变化单位。

论文真正要回答的，正是怎样让一次局部替换不必以整个系统重新开始为代价。下面先不沿着公式走，而是从一次具体替换出发，看看工程上会推导出什么设计。

# 从动态替换反推 Cordis

假设 Agent 原本通过本地文件系统插件读写工作区，现在准备改用远端 Code Server 环境的文件服务。旧实现持有文件句柄、目录监听和缓存，新实现依赖网络传输与鉴权；上层的编辑、搜索和索引插件，则希望继续通过同一套文件接口工作。
我们希望旧资源能够释放，受影响的使用方正确退出并重新绑定，无关的模型服务和会话存储继续运行。已经保存的业务文件当然不能因为插件卸载而一起删除。
这些要求分成两个方向。**时间可组合性（temporal composability）**关心怎样撤回插件对受管状态的贡献；**空间可组合性（spatial composability）**关心依赖怎样组合、隔离，并在变化时协调。先看第一个问题。

## 怎样只撤销旧插件

在“万物皆插件”的系统里，插件也是卸载和替换的单位。运行时要拿掉其中一个，就必须分清它和其他插件分别留下了什么。安全卸载不是让整个系统倒退到历史快照，而是只撤销目标插件的贡献。

因此，首先需要的是归属边界。那些不与外界交互、也不被外界持有的局部对象，不是这里的问题；我们需要处理的是越过插件边界的修改，例如注册目录监听、占用文件句柄，以及向 Context 提供服务。它们必须能够归到对应的插件实例上。
但知道“是谁做的”，还不等于可以安全地拆走它。两个插件可能共同使用一个服务，如果 A 的清理会破坏 B 的结果，就不能把 A 当成独立的撤销单位。这里还需要独立性，让一方的执行和撤销不改变另一方的行为。确实存在先后关系的部分，则要把顺序表达出来，不能强行视作独立。

工具注册表可以说明这个区别。A 用唯一名称注册 `format_document`，B 注册 `search_symbol`；各自卸载时只删除自己的条目。如果表只按名称查询，不把插入顺序作为公开语义，那么移除 A 就不影响 B。这里的独立性来自服务主动设计的精确注册和删除，而不是因为 A、B 恰好放在两个插件文件里。
反过来，允许同名覆盖，或者清理时直接清空整张表，就会破坏这个约定。两个插件即使都写了 cleanup，也未必能够独立卸载。

有了归属和独立性这两层边界，我们才可以缩小视角，研究一个插件本身。它的一次加载，对外可以看成一组副作用；卸载则要撤回这一整组修改。
这里的“撤回”不必是逐字节还原。监听器关闭以后，操作系统的内部计数器可能变了；释放内存以后，堆的布局也不会恢复原样。固定其他插件的贡献，只要通过模型允许的操作无法区分安装前与撤销后的受管状态，就足以认为这次修改已经撤回。这叫**观察等价（observational equivalence）**。它允许忽略实现细节，却不能忽略接口仍然能够观察到的差别。

接下来的问题，就是如何完整撤销这组副作用。运行时面对任意 JavaScript 代码，不可能在卸载时才猜测它改过什么、该怎样恢复。知道这些信息的是执行操作的代码，所以撤销方法必须在副作用发生时就交出来，再由上层统一管理。

顺着资源管理的工程直觉，这些撤销函数应该归入当前插件实例，并按执行的反序调用。后创建的资源往往依赖先创建的资源，打开连接以后再建立监听，退出时就先移除监听，再关闭连接。每来一个新的撤销函数，就把它接到已有清理逻辑的前面，自然得到后进先出的**撤销累加器（accumulator）**。
这样，插件内部即使分成多个辅助函数，也不需要在卸载回调里重新罗列所有资源。每一处取得资源的代码交出自己的撤销方法，外层只负责组合和调度。

![图 2：假设 A、B 的操作独立。卸载 A 时反序撤回 A₂、A₁，B 的贡献保留。](./figures/02-selective-undo.svg)

到这里，API 的样子几乎已经呼之欲出了。执行操作的代码返回清理方法，把何时清理的控制权交给框架。这正是前端开发者熟悉的 `useEffect` 范式：

```ts?lsp=false
useEffect(() => {
  const watcher = fileService.watch(workspace, onChange)
  return () => watcher.close()
}, [fileService, workspace])
```

Cordis 的 `ctx.effect` 也采用类似的形式：

```ts?lsp=false
ctx.effect(() => {
  const watcher = localFs.watch(workspace, onChange)
  return () => watcher.close()
})
```

关键在于返回函数承担的约定。[React 的 `useEffect`](https://react.dev/reference/react/useEffect) 会在规定时机调用 cleanup，也要求开发者正确清理，但 API 不会证明它确实撤销了对应操作。Cordis 的形式化模型则把这一点当作前提：返回的 inverse 必须使这次修改得到撤销，才能继续推导组合后的保证。Cordis 同样不会替开发者证明一个随手写下的回调正确。

于是，从“怎样单独卸载插件”，我们走到了归属明确、交出撤销方法的单次副作用。怎样把它们组合回一个可撤销插件，是后面论文论证要完成的事。

## 怎样只让相关插件跟着变化

前面要求独立的是对共享环境的修改，不是在消除服务之间的依赖。文件服务被替换，索引插件仍然需要跟着调整；与文件服务无关的插件，则不应因此退出。
要确定这个范围，运行时需要一张随当前绑定更新的依赖图。不过，整张图不必由某个插件集中描述。使用方声明需要什么，供给方登记能提供什么，运行时把两端连接起来，就能从局部关系得到整体关系，也能反向查出谁依赖谁。

视角由此缩小到一个插件对环境的要求。远端文件服务需要网络和鉴权，索引插件需要文件读写和监听。这就是论文所说的上下文需求。
怎样把需求表达给系统，本身已有很多工程方案。静态 `import`、插件的依赖清单、DI 的装饰器，都能表达某一层次的依赖；响应式系统还会从实际读取中被动收集关系。论文没有比较这些方案，而是选定执行前显式声明的模型，我们也沿着这个选择继续往下看。

索引插件需要的是文件系统能力，而不应该把某个本地实现写死在声明里。否则替换文件服务，就得连使用方代码一起修改。我们需要为这项稳定的需求取一个名称，也就是**依赖键（dependency key）**。使用方声明需要 `fs`，供给方登记符合接口约定的实现，运行时决定这次绑定到谁。

DSH 使用的 Cordis 通过 `inject` 表达这类声明。下面沿用假设的 `fs` 服务，省略类型扩充和索引实现，API 形式见[官方服务与依赖文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/framework/service.md)：

```ts?lsp=false
import type { Context } from '@deepseek-ai/cordis'

export const inject = ['fs']

export function apply(ctx: Context) {
  const fs = ctx.fs
  // 使用本次绑定的文件服务建立索引。
}
```

供给方则通过 [`ctx.provide`](https://github.com/deepseek-ai/deepseek-harness/blob/master/vendor/cordis/src/reflect.ts) 登记已经创建好的服务：

```ts?lsp=false
ctx.provide('fs', remoteFs)
```

`inject` 表达需求，`provide` 登记供给，`ctx.fs` 取得当前绑定。运行时不需要理解索引算法，只需要知道这些局部关系。
依赖变化后的传播，也可以按熟悉的发布订阅机制理解。声明提供了订阅依据，服务供给发生变化时，运行时[通知相关插件](https://github.com/deepseek-ai/deepseek-harness/blob/master/vendor/cordis/src/reflect.ts)重新检查依赖。通知不是变化本身，它只是让系统知道哪些插件需要重新协调；具体怎样退出和进入，还要结合前面的撤销机制。

## 两个方向在 Context 汇合

现在可以把两条线接起来了。索引插件先清理旧文件服务上的监听，旧服务随后退出；远端实现及其底层依赖准备好以后，索引插件重新取得 `fs`，建立新的监听。运行时把这些加载和退出规则组织起来，就得到了生命周期。

Cordis 用 Context 同时承载两类信息。副作用经它追踪，撤销方法因此能归到正确的插件实例；服务也经它提供和取得，依赖绑定因此能被运行时管理。提供服务本身又是一项副作用，供给方退出时，自己加入的绑定也要撤回。
这就是论文的**上下文范式（context paradigm）**。Context 不只是一个方便取服务的容器，它把“改过什么”和“依赖什么”放进同一套运行时结构。不过，这是一份编程约定，不是安全沙箱；绕开它修改共享状态，就不能直接套用这份保证。

从系统需求一路向下，插件最终被拆成了可以管理的修改和依赖。运行时能够安全组合插件，依靠的不是理解插件的全部业务逻辑，而是这些局部信息足够明确。

# 论文怎样把结论证明回来

前面是工程上常见的自上而下思路，先问系统需要什么，再拆出机制和 API。论文的方向恰好相反。它从最小单元出发，证明局部约定可以逐层组合，最后回到整个动态系统。下面只保留这条推进路线和关键结论。

![图 3：工程思路向下拆解需求，论文论证向上组合局部保证。](./figures/03-design-and-proof.svg)

## 从单个副作用到单个插件

一次副作用改变状态，同时交出撤销函数，这是 [Definition 8](https://arxiv.org/pdf/2608.25512#page=12) 的基本约定。沿用前文的观察等价口径，可以简写为：

$$$
\begin{aligned}
e(\gamma) &= (\delta, g) \\
g(\delta) &\simeq \gamma
\end{aligned}
$$$

执行$e$，状态从$\gamma$ 变为$\delta$，得到撤销函数$g$；执行$g$，则应恢复到与原状态观察等价的状态。原文先用严格等式定义，随后在第 3.3 节按观察等价推广。这里需要的是撤销本次实际执行，而不是找到一个对所有状态都通用的逆变换。

接下来把 A、B 两次操作组合起来。正向先 A 后 B，撤销先 B 后 A；B 撤销以后，A 的撤销函数重新遇到自己执行后留下的状态，所以整个组合仍然满足同一份约定。这就是 [Theorem 11](https://arxiv.org/pdf/2608.25512#page=13) 的 *Witnessing survives effect composition*。

关键是，组合结果仍然是同一种单元。A、B 的整体还可以与 C 组合，不需要重新打开 A、B 的内部实现。一份局部保证，就这样传递给更大的组合。
把组合改成逐步积累，得到的就是前面的撤销累加器。[Theorem 16](https://arxiv.org/pdf/2608.25512#page=15) 保证，每次反序撤销都恢复对应步骤之前的状态，中间的正确性不变量也得到保持。

论文用**副作用迭代器（effect iterator）**表示这段逐步执行的过程。每完成一步，交出撤销方法和可能存在的下一步；加载运行它，卸载撤回已经完成的部分。单次副作用的保证于是组合成了插件的局部时间可组合性。
再给插件加上依赖声明，以依赖是否满足决定启停，就得到了[局部空间可组合性](https://arxiv.org/pdf/2608.25512#page=18)。至此，我们有了一个知道怎样运行、怎样撤销、何时可以运行的插件。

## 从单个插件到多个插件

下一块积木是独立性。前面按工程经验划出的边界，论文也把它变成了明确条件。

对于不同依赖键，[Definition 29](https://arxiv.org/pdf/2608.25512#page=21) 要求操作及其撤销只读写对应绑定，才有 [Theorem 45](https://arxiv.org/pdf/2608.25512#page=29) 的“不同键上的操作独立”。这里隔离的是实际访问范围，不只是名称。两个服务背后仍然修改同一个文件，就不能因为分别叫 `fsA`、`fsB` 而认为它们独立。

对于同一个键，[Definition 46](https://arxiv.org/pdf/2608.25512#page=29) 把可交换性的证明责任放在能力提供方。前面的注册表只有在精确删除各自条目、操作顺序不影响公开行为时，才能提供这种保证。使用方无法单靠声明依赖，弥补一个“卸载时清空整张表”的 API。
独立性不仅要求正向操作能够交换，还约束撤销及返回结果；完整条件见 [Definition 42](https://arxiv.org/pdf/2608.25512#page=27) 和 [Definition 44](https://arxiv.org/pdf/2608.25512#page=28)。

这些单次操作的条件，又能向上传给整个插件。[Theorem 47](https://arxiv.org/pdf/2608.25512#page=30) 的结论可以概括为：

> 双方提供的键都不落入对方使用或提供的范围，共同操作的键又满足可交换性要求，那么两个经 Context 中介的副作用迭代器相互独立。

这样就不用每次组合插件，都重新检查全部业务代码；可以依据声明和能力接口已经履行的约定来判断。对两两独立的副作用，[Theorem 43](https://arxiv.org/pdf/2608.25512#page=28) 还允许按任意排列执行本次产生的全部撤销函数。独立单元不必挤在一条全局撤销栈里，插件内部有先后关系的步骤则仍按反序撤回。

索引插件和文件服务显然不是这种独立关系。它们的顺序必须交给依赖拓扑处理。能交换的部分靠独立性，不能交换的部分显式保留顺序，下一步才是把它们放进同一个运行时。

## 把插件放进生命周期

插件定义描述需求、供给和加载过程，插件实例则持有实际绑定、撤销累加器与当前状态。第四章用一组带前置条件的转移规则管理它们，主要状态如下：

![图 4：四个主要状态。加载中途也可转向卸载，清理完成后才可能开始下一轮。](./figures/04-plugin-lifecycle.svg)

先前的依赖图告诉运行时“现在应该绑定谁”，论文称之为**目标依赖视图（target view）**。依赖完整以后，实例提交这份解析结果并开始加载；实际采用的**已提交依赖视图（committed view）**在本轮加载、运行和清理期间保持稳定。

所以，依赖变化不是直接把实例手里的旧引用换成新引用。索引插件要先借助旧文件服务完成清理，再用新绑定开始下一轮。加载中途发生变化，也会改道卸载，撤回已经完成的部分。
相应地，供给方准备好以后使用方才能加载；使用方清理结束以后，供给方才能完成卸载。[Theorem 70](https://arxiv.org/pdf/2608.25512#page=47) 与 [Theorem 71](https://arxiv.org/pdf/2608.25512#page=48) 保证了这份顺序和绑定的一致性。

论文还把**退役（retire）**与移除分开。退役是不再开启新的生命周期，不是立即删除实例。清理、子实例处理等工作完成以后，才能真正从注册表移除它。这样，退出请求不会把仍被清理过程需要的运行时对象提前删掉。

## 最终得到哪些系统性质

上述规则先保证每一步合法变化都保持插件图的结构约束，也就是 [Theorem 64](https://arxiv.org/pdf/2608.25512#page=43) 的**保持性（preservation）**。在这个基础上，[Theorem 68](https://arxiv.org/pdf/2608.25512#page=46) 给出**精确恢复性（recovery exactness）**：即使其他插件的步骤穿插其中，目标插件的累加器仍然能撤回自身对受管状态的贡献，保留其他插件的贡献。这才把单段序列的撤销保证，推到了动态系统里。

系统还需要能完成协调。[Theorem 73](https://arxiv.org/pdf/2608.25512#page=49) 的**进展性（progress）**说明，在无环、有界、实例总量有限等条件下，外部停止持续编排后，剩余生命周期过程能够到达**静止状态（quiescence）**，不再有待执行的生命周期步骤。

最后，不同的合法调度会不会留下不同终态？[Theorem 80](https://arxiv.org/pdf/2608.25512#page=54) 的**合流性（confluence）**给出如下结论，这里作简要译述：

> 从相同初始状态出发，执行相同编排步骤并保持它们的顺序，不同合法调度到达的静止状态观察等价，允许对无关的实例名称作一致重命名。

它还给出一种静态理解方式。在定理条件下，最终受管状态等价于从同一初始环境出发，按依赖顺序组装最终保持激活的插件。这不是说任意两段历史只要最终配置相同就必然等价，而是对模型中的合法变化及其终态作出的保证。

从一次操作，到一个插件，再到交错运行的整个系统，前面的局部约定终于组合成了最初想要的能力。

## 这些结论成立到哪里

首先，撤销和独立性必须由实现兑现，需要保证的共享交互必须经过 Context。运行时负责按规则组织它们，不会自动证明任意插件代码符合约定。

进展性还要求依赖优先关系无环、整个过程中出现的实例总量有限、副作用迭代有界。无限创建实例、某一步永远不返回、配置持续变化，都不能套用终止保证。静止也不是“所有插件成功激活”，缺少依赖的插件可以保持未激活。

合流性还要求插件激活完成时实际提供声明中的全部键，即 [Definition 76](https://arxiv.org/pdf/2608.25512#page=52) 的完全履行供给声明；[失败扩展](https://arxiv.org/pdf/2608.25512#page=56)则明确将失败情形排除在合流结论之外。已完成部分可以按约定撤销，不代表成功与失败两条轨迹会得到相同终态。

最后，比较的是受管状态，不是外部世界的历史。文件服务卸载，不会让已经发送的请求消失；两次调度终态等价，也不意味着中间发送消息的顺序相同。[论文对此作了明确区分](https://arxiv.org/pdf/2608.25512#page=55)。因此，“可撤销”不能泛化成整个业务过程都可回滚。

# 从前端视角对它的评价

## 熟悉的机制，和不那么显然的保证

从前端经验看，我最初的感受没有变。副作用与清理成对、资源交给上层管理、显式依赖、变化通知、根据目标调整实例状态，这些都不是什么陌生的工程做法。只看“万物皆插件”和一个形似 `useEffect` 的 API，确实很难让我觉得出现了全新的架构思想。

但读完以后，我觉得需要把两种判断分开。熟悉这些机制，意味着我们很可能也会选择类似设计；它不意味着我们已经知道，这些设计组合起来以后，在什么条件下仍然正确。
例如，先清理监听再关闭连接，几乎是资源管理的直觉。可一旦允许别的插件在中间工作，还要单独卸载其中一项，就不能只靠一条反序清理链回答问题。需要进一步说明哪些操作独立、哪些操作必须排序，以及依赖改变时谁仍然有权使用旧服务。论文把这些问题连成了一条可以检查的论证。

我认为形式化的价值就在这里。它把“应该能清理干净”“这两个插件应该互不影响”变成了明确约定，既给出组合后的结论，也暴露了直觉跨过去的前提。
其中尤其值得注意的是，撤销方法和依赖关系都不再只存在于开发者的理解里。运行时实际持有它们，并据此组织组合过程。论文称之为具象化，放到工程里看，就是把原本需要人手协调的信息，变成程序能够直接管理的对象。

因此，我更愿意把创新概括为整套动态组合机制的组织与形式化，而不是某一个 API 的发明。它没有使已有工程经验失效，反而解释了这些经验为什么能配合工作，以及在哪些地方会失效。对我来说，最值得学习的，是它如何把接口设计与系统保证连起来。

## 保证背后的工程责任

这套模型的一个直接价值，是让正确性可以随接口复用。能力提供方把资源取得、撤销和独立性封装好，使用方遵守声明，运行时安排生命周期；新增一个插件时，就不必重新理解整个系统的全部实现。

但提供方得先把约定做对。不能在 API 内部偷偷修改不属于自己的共享状态，也不能交出会破坏其他使用方的撤销函数。普通业务插件未必需要自己实现所有清理机制，真正提供共享能力的那一层却必须承担这份责任。使用 Context 是进入模型的条件，不是代码正确的认证。

资源的生命周期也要重新审视。目录监听可以随着索引插件退出，但需要跨越插件替换的会话记录，不能只寄存在那个临时实例里。它应交给生命周期更长的服务或持久化存储。运行时能撤销和重新加载，不代表它会自动迁移旧实例的全部业务状态。
同样，决定哪些部分可以独立变化，会影响插件怎么拆、依赖怎么声明。这些结构要由开发者维护，细分本身也会增加理解成本。插件越多，并不自动意味着设计越好。

另外，编程约定不等于安全隔离。插件若仍拥有宿主权限，就可能绕过 Context 访问外部资源。尤其当代码由模型生成时，组合正确性、生成代码的可靠性和沙箱边界仍然需要分别处理。不能因为运行时有了形式化论证，就把另外两项责任一起交给它。

所以，是否值得采用，还是要看系统是否真的需要持续改变自己的组合。插件在启动时确定、更新可以通过重启完成，未必需要承担全部动态管理成本；如果系统要维持长期会话，并反复替换相互依赖的能力，那么明确资源归属、依赖绑定和退出顺序，就有很实际的价值。

# 最后回到 DSH

回到开头，“Agent Loop 也是插件”确实是 [DSH 官方架构](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.zh.md)的一部分。但循环实现可以替换，与替换后更会规划、更能完成任务，是两个问题。

显式启用的 [`dsh-tool-cordis`](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/extensions/tool-cordis/README.zh.md)允许模型定义、运行和停止当前进程中的临时插件，可以作为探索这一方向的入口。不过，它不会自动持久安装这些插件，也没有解决怎样选择改动、验证代码和评价效果的问题。论文[结论](https://arxiv.org/pdf/2608.25512#page=83)也把持续生成和替换 Harness 插件的自演化场景，放在未来验证方向里。

我原本想从论文里学习 Agent 怎样工作，最后更有收获的问题却是，当系统连自身结构都能改变时，怎样让这种变化仍然可理解、可撤销、可协调。前端经验让我认出了其中的工程做法，论文则让我重新理解，它们需要满足什么条件，才能共同支撑一个持续变化的系统。
